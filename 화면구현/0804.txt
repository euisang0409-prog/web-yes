내외부 연계 모듈 구현 환경

내외부 연계
서로 다른 시스템이 데이터를 주고받으며 함께 동작하도록 연결하는 것
최근 회사에서는 하나의 프로그램만 사용하는 경우가 거의 없다
예를 들어 쇼핑몰에서는 회원관리 프로그램, 주문 프로그램, 결제 시스템, 배송 시스템, 재고 시스템 등 여러 프로그램이 각각 존재한다

이 시스템들이 서로 정보를 주고받아야 정상적으로 업무가 진행된다.

내외부 연계 모듈 구현 환경
서로 다른 시스템간 데이터 교환 및 서비스 연계를 실현하기 위해 필요한 기술적 물리적 실행 환경

- 데이터베이스
- 인터페이스 테이블
- 프로그램
- API
- 네트워크
- 서버
- 보안
- 로그시스템

구현 방식
1. DBMS 오브젝트
DBMS 내부에서 제공하는 기능을 이용하여 데이터를 자동으로 연계 하는 방식
- 프로그램을 별도로 작성하지 않고 데이터베이스 자체기능을 이용하여 다른 시스템으로 데이터를 전달한다
- 대표적으로 Trigger, Procedure를 사용한다
- 쇼핑몰에서 주문이 발생하면 -> Trigger 실행 -> 인터페이스 테이블에 저장 -> 수신 시스템이 읽어간다

장점
- 구현이 비교적 쉽다
- 별도의 프로그램이 적다
- DB 내부에서 처리하므로 속도가 빠르다
- 소규모 시스템에 적합하다

단점
- DB에 부하가 발생한다
- DBMS에 종속된다
- 시스템이 커질수록 관리가 어렵다
- 확장성이 낮다


2. 프로그램 코드
- Java, Spring, Python 등의 프로그래밍 언어를 이용하여 연계 프로그램을 직접 개발하는 방식이다.
- 데이터를 추출하고 필요한 형태로 형변환 후 다른 시스템으로 전송하는 모든 과정을 개발자가 직접 구현한다.
- DB연결, 데이터 조회, 데이터 검증, 데이터 변환, JSON또는 XML 생성, API 호출, 로그 기록, 오류 처리

장점
- 자유롭게 개발이 가능하다
- 다양한 기능을 추가할 수 있다
- 복잡한 업무 처리에 적합하다
- 유지보수가 비교적 쉽다
단점
- 개발 시간이 오래걸린다
- 개발자의 기술 수준에 영향을 많이 받는다
- 테스트가 많이 필요하다

3. EAI / ESB 방식
기업에서 사용하는 수많은 시스템을 하나의 통합 플랫폼으로 연결하는 방식
- 기업에는 ERP, CRM, 인사, 그룹웨어, 물류, 회계, 모바일 앱 등의 수십 개의 시스템이 존재한다
- 중간에 EAI 또는 ESB를 두어 모든 데이터를 관리한다
EAI : 기업 내부 시스템을 하나로 통합하는 미들웨어
ESB : 서비스간 데이터를 전달하는 버스(BUS)형태의 미들웨어

장점
- 대규모 시스템에 적합하다
- 시스템 추가가 쉽다
- 중앙에서 관리할 수 있다.
- 장애 관리가 쉽다
단점
- 구축 비용이 높다
- 구조가 복잡하다
- 운영 인력이 필요하다

4. Web Service 방식
- 인터넷이나 네트워크를 이용하여 표준화된 방식으로 시스템 간 데이터를 주고받는 방식
- 예전에는 SOAP을 많이 사용했지만, 최근에는 대부분 REST API를 이용하여 데이터를 주고받는다.

장점
- 개발이 쉽다
- 다양한 언어와 플랫폼에서 사용할 수 있다
- 확장성이 높다
- 클라우드 환경에 적합하다
단점
- 네트워크 장애의 영향을 받는다
- 보안 설정이 중요하다
- API버전 관리가 필요하다

5. API / 클라우드 연계 방식
- 클라우드와 MSA 환경에서 REST API, gRPC, Kafka 등의 이벤트 스트리밍을 활용하여 시스템 연계하며 API Gateway와 Service Mesh를 통해 서비스 간 통신, 보안, 모니터링을 관리한다.

API Gateway : 여러 서비스로 들어가는 요청을 한 곳에서 받아서 적절한 서비스로 전달하는 안내 데스크 역할

GET / aip/orders/10

Service Mesh : MSA에서 서비스 간 통신을 관리하는 기술

장점
- 확장성이 우수하다
- 경량 구조이다
- 실시간 이벤트 처리가 가능하다
단점
- 초기 아키텍처 설계가 복잡하다
- API 버전 관리가 필요하다
- 보안 체계가 필요하다
- 장애 추적이 어렵다

하이브리드 연계
- 기존에 사용하던 온프레미스 시스템과 새롭게 도입한 클라우드 또는 SaaS 시스템을 함께 연결하는 방식
- 많은 기업이 기존 시스템을 한 번에 모두 클라우드로 이전할 수 없다
- 기존 시스템에는 중요한 데이터와 업무 기능이 많고, 교체 비용과 위험도 크기 때문이다.

db기반 + EAI 

DB기반 + API Gateway

EAI + API Gateway

장점
- 현실적인 이전 및 확장 전략이 가능하다
- 기존 레거시 자산을 활용할 수 있다.
- 클라우드 기능을 선택적으로 사용할 수 있다.

단점
- 관리가 복잡하다.
- 운영비용이 증가한다
- 데이터 일관성 관리가 어렵다
- 네트워크 의존성이 높아진다.

내외부 연계 모듈 구현 환경의 필요성
1. 이기종 시스템 간 데이터 통합
- 시스템별로 사용하는 db가 다를 수 있따
- 이렇게 서로 다른 시스템을 하나로 연결해주는 것이 연계이다
2. 업무 프로세스 자동화 및 효율성 제고
- 데이터 흐름 자동화와 실시간 또는 배치 처리가 가능하다
자동화 : 사람이 직접 입력하지 않아도 프로그램이 자동으로 처리하는 것
실시간 처리 : 주문이 측시 처리된다.
배치 처리 : 한 번에 모아서 처리한다

3. 안정성 및 오류 대응
오류 로깅, 예외 처리, 장애 복구를 통해 신뢰성을 확보한다 

오류 로깅 : 프로그램에서 발생한 모든 작업 기록

예외 처리 : 오류가 발생해도 프로그램이 종료되지 않도록 처리

장애 복구 : 일시적인 장애가 발생하면 데이터를 다시 전송하거나 이전 상태로 복원한다

4. 확장성 확보
- 클라우드와 분산 환경에서도 유연하게 연계할 수 있어야 한다.

확장성 : 사용자가 증가하거나 서비스가 늘어나도 시스템을 쉽게 확장할 수 있는 능력

5. 표준화 및 상호 운용성
- Restful API, OpenAPI, JSON/XML 기반 데이터 포맷 활용 및 글로벌 표준을 준수하여 표준화 및 상호 운용성을 확보할 필요가 있다.

6.  최신 동향 반영
- 이벤트 중심 아키텍처
- 서버리스 컴퓨팅
- AI 기반 연계 관리

연계 모듈 구현 환경 구축
1. 연계 모듈 구현 환경 변경 사항을 파악한다
먼저 연계 방식을 결정한다.
- 테이블 방식 : 인터페이스 테이블을 이용하여 데이터를 전달
ㄴ 실시간 처리, 데이터 양이 많을 때, 안정성 중시
- 파일 방식 : XML같은 파일을 이용하여 연계 데이터를 전달
ㄴ 하루에 한 번 전송, 대량 데이터, 외부 기관

2. EAI / ESB 기반 연계 모듈 구현 환경 구축
2-1. 연계 DB 및 계정을 생성한다.   
운영 DB와 연계 DB의 목적이 다르기 때문에 분리하는게 원칙
2-2. 연계를 위한 테이블 생성
- 연계 데이터를 저장하는 연계 테이블
- 송수신 이력 및 오류 확인을 위한 로그테이블
ㄴ 장애가 발생하면 어디서 실패했는지 알 수 있다.
- 코드 매핑 및 변환을 위한 매핑 테이블
- 오류 처리를 위한 오류 코드 테이블

2-3. 연계 응용 프로그램 구현
송신 시스템이랑 수신 시스템에서 각각 구현
- 송신 시스템의 연계 응용 프로그램은 운영 DB에서 데이터를 추출하고 송신시스템의 코드를 수신시스템의 코드로 변환하는 작업 처리
- 수신 시스템의 연계 응용 프로그램은 연계 테이블의 데이터에 대해 유효성을 점검하고, 운영 DB에 반영하는 작업 처리

3. 웹 서비스 방식에 의한 연계 모듈 구현환경 구성
웹서비스 : 인터넷이나 네트워크를 이용하여 서로 다른 시스템이 데이터를 주고받는 기술
SOAP(Simple Object Access Protocol)
XML 기반의 메시지를 HTTP, HTTPS, SMTP 등의 프로토콜을 이용하여 교환하는 기술
예전에는 대부분의 기업 시스템이 SOAP를 사용했고, 현재는 REST API 형식이 많이 사용하지만, 금융권과 공공기관의 기존 시스템에서는 아직도 SOAP을 사용하는 경우가 많다
UDDI(Universal Description Discovery and Integration)
웹 서비스가 많아지면 어떤 서비스가 있는지 찾기 어렵다
그래서 서비스 목록을 저장하는 저장소가 필요하다
- 서비스 등록
- 서비스 검색
- WSDL 저장

WSDL(Web Service Description Language)
웹 서비스의 상세 정보를 기술한 XML 문서
- 웹 서비스 이름
- 서비스 위치(URL)
- 메시지 형식
- 프로토콜 정보

3-2. 웹 서비스 방식에 의한 연계 모듈 구현 환경 구축하기
- 송수신 파일 생성 위치 및 파일명 정의
송시시스템
송신 연계 파일
로그 파일
오류 로그파일

수신 시스템
수신 연계 파일
로그 파일

- 송신 시스템 연계 응용 프로그램 구현하기
ㄴ 송신 시스템의 운영 DB로부터 연계 데이터를 추출해서 송신 파일을 XML 형식으로 생성하는 자바 프로그램 구현하기
ㄴ 구현된 서비스를 주기적으로 실행하기 위해 스케줄러에 등록한다

- 파일 전송 및 수신 시스템의 DB 반영 서비스 호출을 처리한다
ㄴ 웹 서비스 방식에서 파일 전송은 HTTP 기반의 SOAP를 사용하여 송수신한다
ㄴ 연계 파일을 수신 시스템의 수신 위치로 전송한 후, 전송된 파일 내용을 수신 시스템 운영 DB에 반영하는 서비스를 실행한다

- 수신 시스템의 연계 응용 프로그램을 구현한다
ㄴ WSDL에 기술된 운영 DB에 연계 데이터를 반영하는 서비스를 구현한다
ㄴ 서비스 구현 방식은 송신 시스템의 연계 응용 프로그램과 동일하게 자바를 사용한다
ㄴ 구현한 서비스는 수신 시스템에서 서비스 호출이 가능한 위치에 배치한다

연계 메커니즘 정의서 또는 연계 아키텍처 설계서를 확인 및 점검

연계 메커니즘 정의서란?
- 시스템 간 데이터를 어떻게 주고받을 것인지 구체적으로 정의한 문서

연계 메커니즘 정의서의 내용을 확인한다
연계 방식이 바뀌면 프로그램 구조도 달라지기 때문이다
예를 들어 REST API로 만들던 것을 파일(XML)방식으로 변경하면 프로그램을 새로 수정해야 한다.
- 송수신 시스템의 연계 응용 프로그램 구현 방식
- 연계 데이터 생성 방식
ㄴ 테이블 방식
ㄴ 파일 방식
- 코드 매핑 및 데이터 변환 처리 위치
ㄴ 송신 시스템 : 송신 시스템에서 변환하는 경우가 많다
송신 시스템이 데이터를 표준 형식으로 만들어 보내면 수신 시스템의 부담이 줄어들기 때문이다.
ㄴ 수신 시스템

연계 응용 프로그램 구현 방식을 수정 및 보완한다
처음에는 Trigger 방식으로 설계했지만 프로젝트가 진행되면서 Java프로그램이 더 적합할 수 있따 이 경우 정의서도 함께 수정해야 한다
만약 정의서를 수정하지 않으면 개발자마다 다른 방식으로 구현하게 된다.

연계 데이터 생성 방식을 수정 및 보완한다
실시간으로 관리해야 하는 대량 데이터 -> 테이블
모아서 한번에 보내는 대량 데이터 -> 파일

코드 매핑 테이블 생성 위치를 수정 및 보완한다
코드 매핑 테이블 생성 위치를 송신 시스템의 운영DB로 연계 메커니즘 정의서에 수정및 보완
송신 시스템에 두는 이유 : 송신 시스템에서 먼저 변환하면 수신쪽에서 변환 없이 바로 사용할 수 있다.
- 수신 시스템이 단순해진다
- 처리 속도가 빨라진다
- 코드 관리가 쉬워진다.

연관된 내용을 일관되게 수정 및 보완한다
- 연계 응용 프로그램 구현 방식과 연계 데이터 생성 방식의 변경으로 영향을 받거나 연관된 부분이 있는지 확인하여 일관된 내용으로 수정 및 보완한다.
- 문서와 실제 구현이 다르면 프로젝트 전체에 혼란이 발생한다 

송신 시스템의 연계 모듈 구현 환경을 구축한다
1. DBMS 환경을 점검한다
- 송신용 데이터베이스 사용자 생성 여부
- 송신용 데이터베이스 사용자 및 비밀번호로 접근 가능한지 여부

송/수신 시스템의 연계 응용 프로그램을 개발한다

- 설치된 자바 버전
- 설치 경고
- 환경 변수 설정 상태
- 정상적인 명령어 실행 여부

명령어와 옵션을 통해 설치된 자바 개발 도구의 버전을 확인할 수 있으며, 설치 경로 등 정상적인 설치 여부와 설치 환경을 확인한다.

2. 송신 시스템의 연계 응용 프로그램 설계서를 작성한다
- 개발할 송신 시스템 연계 응용 프로그램의 설계서를 작성한다
- 프로그램 설계서는 다음 내용을 포함하여 작성
ㄴ 프로그램 ID
ㄴ 프로그램 명
ㄴ 인터페이스 파라미터
ㄴ 상세 처리 로직
ㄴ 오류 처리 방법
ㄴ 입출력 파일 정보

상세 처리 로직은 자바 언어의 문법으로 구체적이며 중요 내용의 누락 없이 작성한다

송신 시스템 연계 응용 프로그램의 상세 처리 절차
1. 데이터베이스 연결 생성
2. 파일 생성
3. 데이터 추출
4. 코드 매핑
5. 데이터 변환
6. 연계 파일 기록
7. 오류 로그 기록
8. 오류 로그 기록

수신 시스템의 연계 응용 프로그램 설계서를 작성한다
1. 수신 시스템 연계 응용 프로그램 설계서를 작성한다
2. 프로그램 설계서의 상세 처리 로직을 작성한다.
3. 수신용 연계 파일을 한 행 씩 로드한다
- 수신용 연계 파일을 읽기모드로 열고, 파일의 데이터를 한 행씩 로드한다
4. 데이터를 각 속성으로 분할한다
- 파일에서 로드한 데이터를 구분자인 콜론 ( : )을 기준으로 각 속성으로 분할한다
5. 각 속성의 데이터 유효성을 점검한다
- 비어있는 문자열 여부
- 필수 값 누락 여부
- 데이터 타입
- 데이터 길이
- 날짜 형식
- 숫자 형식
- 허용된 값인 여부
6. 코드의 유효성을 확인한다
- 분할된 속성 중 코드가 존재할 경우, 해당 코드가 수신용 코드 테이블에 존재하는지 확인한다
7. 수신용 DB에 데이터를 반영한다
- 행의 모든 속성이 데이터 유효성 점검을 통과하여 유효한 경우 변경 구분자에 따라 수신용 DB의 공고 정보 테이블에 데이터를 반영한다.
8. 처리 단계별 로그를 기록한다
- 연계 파일 읽기 모드 생성
- 연계 파일 열기
- 데이터 로드
- 각 속성 분할
- 데이터 유효성 점검
- 처리 완료
9. 처리 단계별로 오류를 기록한다
- 처리 단계별로 오류가 발생하거나 데이터 유효성 점검 결과 유효하지 않은 값이 발견되면 수신용 오류 코드 테이블을 참고하여 수신용 오류 로그 파일에 기록한다

송수신 연계 응용 프로그램을 단독 배치형식으로 개발한다
- 작성한 송/수신 시스템의 연계 응용 프로그램 설계서 내용을 자바 언어를 사용하여 단독 배치 형식으로 개발한다
- 단독 배치 형식은 웹 화면이나 사용자의 직접 요청 없이 자바 프로그램이 독립적으로 실행되어 정해진 작업을 처리하는 방식이다.
